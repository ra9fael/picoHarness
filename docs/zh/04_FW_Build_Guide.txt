PicoHarness 构建说明

本篇讲怎么从源码做出交付物、怎么部署到板子、以及改完代码怎么验证。
使用方式见 "01_GUIApp_FW_Manual"，接口定义见 "02_Library_User_Guide"。


[前提条件]

以下版本已验证可用：

Node.js：24.18.0
npm：随 Node 附带
浏览器：桌面版 Chrome 或 Edge（需要 Web Serial API）
开发板：Raspberry Pi Pico 2（rp2350a）
设备固件：CircuitPython 10.3.1（board_id：raspberry_pi_pico2）

仓库依赖只有 esbuild、typescript 和两个前端运行时（xterm.js）。安装：

    npm install

设备侧需要一个 asyncio 实现（CircuitPython 不内置）。用 circup 装到板子的 lib 目录：

    circup install asyncio

装完 CIRCUITPY 卷下应存在 lib/asyncio/ 与 lib/adafruit_ticks.mpy。
PIO 那台 PWM 发生器还要 lib/adafruit_pioasm.mpy（circup install adafruit_pioasm）。
仓库在 src/fw/lib/adafruit_pioasm.mpy 存了一份同文件的副本（circup 装出来的原件，sha256
27e3d1fd56ec66c63119acae6b3ef9da5fbe25ed8308647bd549206aa9bf4687），装不了 circup 时直接拷它。
rp2pio 本身已经编进 CircuitPython 10.3.1 的 RP2 构建里，不用装；缺 pioasm 时 code.py 照跑，
只是 caps 里没有 pwm_pio，界面的 HW/PIO 选择不出现。
以后动设备库一律走 circup，不要手工拷贝。


[交付物构建]

    npm run build

产物是单文件 dist/index.html（JS/CSS 全部内联，约 400 KB），双击即可在 file:// 下使用，
不需要起服务器。dist/ 已被 git 忽略，不要提交。


[固件部署]

固件是两个文件：src/fw/boot.py（开双 CDC + 把卷对代码挂成可写）和 src/fw/code.py（协议本体），
都要拷到 CIRCUITPY 卷根目录（下文记作 G:）：

    cp src/fw/boot.py /g/boot.py
    cp src/fw/code.py /g/code.py

注意：

写入后板子立即软复位，正在连接的 Web Serial 会掉线，需要在界面重新点 Connect。
boot.py 只在硬复位时生效（按 RESET 或重新上电；Ctrl-D 软重启不会重跑它）。
刚拷完 boot.py 请硬复位一次，否则设备仍只有一个 CDC 口，caps.usb.data 会是 false。
不想走到板前就发 {"cmd":"reset"}：它先回 {"reset":"pending"}，约 0.25 秒后调
microcontroller.reset()，效果等同于按 RESET——boot.py 会重跑。
G: 根目录若存在 main.py，CircuitPython 就不会再运行 code.py（main.py 优先级更高）。
boot.py 里只有 usb_cdc.enable(...) 和 storage.remount(...) 两件事，不要占 GP0/GP1、
更不要提前建总线对象——引脚裁决者在 code.py 里，boot.py 抢了串口控制台就没法用了。
remount 那行的两个参数都是实测出来的，别"顺手收紧"：只写 readonly=False 的话板子能写了，
但 Windows 会彻底失去对 G: 的写权限（拷文件报 Read-only file system），只能靠安全模式
（连按两次 RESET，此时 boot.py 与 code.py 都不跑）把卷拿回来；带上
disable_concurrent_write_protection=True 才是两边都能写。代价是 Windows 看 G: 是缓存，
板子写了什么要等卷重新读一次（复位/拔插）才看得见——按界面里的"从板子载入"去确认，别开
资源管理器看；要在 G: 上拖文件部署，先复位一次让两边视图对齐。
G: 上没有 lib/ 时说明 circup 没装成功，code.py 会以 ImportError 起不来。

界面"保存到板子"写的是 G:\config.json（临时文件 config.json.tmp 改名而来）。Web Serial 没有
删除卷上文件的接口，所以 cfg.clear 之外你随时可以自己删：在资源管理器里打开 CIRCUITPY 卷删掉
它就行，code.py 不碰这个文件，除非你让它读。板子被 UF2 重刷或整卷格式化时它自然一起没了。
它只是一个备忘文件，上电不会被执行——开机引脚仍是未配置状态。

双 CDC 之后设备在系统里是两个 COM 口：console 口给 CircuitPython 的横幅/print/回溯/REPL，
data 口跑本项目的 JSON 行协议与二进制帧。两个口共用同一 VID/PID（0x2E8A:0x000B），
设备管理器与 navigator.serial.getInfo() 都区分不了，只有 nonce ping 能认出口色，
界面已经按这个规则自动识别，人工排查时也别靠端口号猜。


[类型检查]

仓库里没有 tsconfig.json。直接跑 npx tsc 会报 TS5058，必须显式给参数：

    npx -p typescript tsc --noEmit --strict \
        --module esnext --target es2020 --moduleResolution bundler \
        --lib es2020,dom --skipLibCheck src/ui/main.ts

npm run build 走的是 esbuild，它只做打包，不做类型检查。改过 .ts 一定要单独跑上面这条。


[验证链]

改固件（code.py）后按顺序做：

1. 语法检查
       .venv/Scripts/python.exe -m py_compile src/fw/code.py
2. 部署到板子（见上）
3. 用 pyserial 直接问设备，确认新命令和字段真的在。双 CDC 之后有两条路：
   - 省事的路：不带参数跑 tools/serial_probe.py。它按 VID/PID 找出两个口，用 nonce ping
     分辨口色，从 console 口重启 code.py，在已挂住的 data 口读开机 ready 广播，
     再依次跑 hello / ping / echo。
   - 自己写脚本：能答 {"cmd":"ping"} 并带回 nonce 的是 data 口（协议），
     另一个是 console 口，只吃控制字节和 REPL 语句。
     先打开 data 口并保持读端、再动手重启：CircuitPython 在没有人持有该端口时
     会直接丢掉 CDC 输出，开机 ready 广播只有已经挂上读端时才收得到。
     重启 code.py：往 console 口发 \x03 停掉当前程序 → 等 0.5 s → 发 \x04；
     第二个 \x04 兜住"第一个只把 REPL 叫醒"的情况。
     REPL 语句必须以 \r\n 结尾，只给 \n 的行会被回显但永不执行。
   脚本要用 venv 里的 python（pyserial 只装在 .venv，系统 pip 不通网）。
   输出走 sys.stdout.buffer.write，GBK 控制台打印 UTF-8 会炸。
   设备启动会先发一段设置终端标题的 ANSI/OSC 转义，粘在 ready JSON 前面且不带换行，
   脚本要用正则剥离或按花括号定位提取。

改界面前按顺序做：

1. 类型检查（见上）
2. npm run build
3. 浏览器打开 dist/index.html 做 DOM 冒烟：断言元素存在、交互生效、控制台无报错。
   没板子也能测大部分逻辑——泳道绑定、拖拽高亮、持久化都不依赖设备。
   认口/日志口/REPL 这类端口逻辑可以用假 navigator.serial（两个内存 FakePort，
   一个答 ping 一个只答 REPL）在无设备环境下跑完整条链路。
   测试结束记得清 localStorage（key：picoharness-config-v1、picoharness-scope-v1）。
4. 改过 README 或 docs/ 下任何 .md：npm run docs:check。它按 GitHub 的标题 slug 规则解析每个
   相对链接和 #锚点，死链不为零就非零退出——发版前必须过这一条。

[排障判据]

界面发了新命令、设备回 "unknown cmd"，或者 gpio.state 应答里缺新字段、
ready.caps 里没有 uart/i2c_pairs/spi —— 这不是前端 bug，是 G:\code.py 还是旧版本。
先比对设备端 code.py 里的 VERSION 字符串与源码，重新拷一次即可。
配置菜单里"保存到板子"那三行不见了，同样这条判据：ready.caps 里没有 cfg。
只看到一个 COM 口、或 ready.caps.usb.data 为 false —— 是 G:\boot.py 没拷进去，
或者拷完没做硬复位（Ctrl-D 不算）。
"保存到板子"报 OSError: [Errno 30] Read-only filesystem —— 同一个根因的另一面：
G:\boot.py 里缺 storage.remount(...)，或者拷了没硬复位。卷对代码仍是只读的，
cfg.get/cfg.clear 会照常应答（读不需要写权限），所以只有写入暴露这个问题。
ready.caps.spi 里的引脚组和别处实测不一致 —— 那是 SPI_GROUPS 这张静态表的问题，
它是 pico-sdk hardware/gpio.h F1 列的完整转录（GP0..GP28 行另有上板实测逐行确认），
开机不做 SPI 扫描，也别去改探测逻辑。注意出厂前它还按 caps.gp 投影一次：
某个脚从组里消失通常是板级定义没声明它，不是表错了。
界面引脚池少脚 / 某脚点不进去，而 caps 数组里有它 —— 先看 ready.gp 在不在、包不包含那个脚；
gp 是这块板能取到的脚的集合（从 board 的 Pin 对象算出来的），缺了就是 G:\code.py 还是旧版本。
离线核对跑 tools/caps_audit.py（--static 把 gpio.h / platform_defs.h / CP 源码里读到的规则
铺满 48 个脚号做自校，并解析固件里的 SPI_GROUPS 与 UART 实例式；接上板子再加真机对账）。

[固件实现要点]

主循环是 asyncio 任务组：command_reader 读 stdin、gpio_monitor 边沿推送、adc_monitor 死区推送、
adc_streamer 波形批量流。每个协程先 create_task 拿到 Task 句柄，再 await gather(t1, t2, ...)。
该 mpy 端口的 gather 只接受 Task 对象，塞裸协程会在 sleep_ms 处触发 "missing await" 断言。

四条真机实测出来的约束，动调度之前务必知道：

1. sys.stdin.read(1) 会阻塞直到至少一个字节到达，它不是"无数据返回 None"的非阻塞惯用法。
   不加门控时 command_reader 第一步就冻结整个事件循环，所有兄弟 monitor 永远得不到步进
   （这正是当初 ADC 读不到数的根因）。双 CDC 后 data 口同理：先读 in_waiting 再 read，
   并把 DATA.timeout 设为 0；单口回落路径仍用 select.poll() 门控 sys.stdin。
2. busio.UART 默认 timeout=1000 ms，一次空读就能把协作式循环整段卡住；建总线时显式 timeout=0。
3. USB CDC 上 print(..., flush=True) 每次写完抛 OSError [Errno 22]（文本已正常输出），不要显式 flush。
4. usb_cdc.Serial 是二进制流：read() 给 bytes、write() 收 bytes-like，
   而 sys.stdin 是文本对象。两者混在一条读取路径里时必须先 decode("utf-8","replace")，
   否则同一处缓冲会同时炸出 TypeError 和半个中文行。

PIO 这路 PWM 的几条实测结论（tools/pio_pwm_probe.py、tools/pio_bg_probe.py、tools/pio_fw_check.py）：
rp2pio 已内置，板上现拼 asm 靠的是 lib/adafruit_pioasm.mpy，所以固件里没有任何 host 端构建步骤；
一段 8 指令的程序，一个周期固定花 8 个 tick，两个计数寄存器各 16 位，于是 SM 时钟实测窗口
2288 Hz–150 MHz 换算成频率就是 0.0174553–15,000,000 Hz，全片 12 个 SM 可共存（Stage 5 实测 12 路
0.1 Hz 同时输出）。正在跑的 SM 会继续照它那条 4 深的 TX FIFO 出货，直接写新计数要等五个周期才见效，
所以 pwm.cfg 对 PIO 通道一律 deinit + 重新 arm，再上 background_write(loop=...)。
构造函数抛异常的 SM 会把引脚占到复位为止，但不回补预算——报错时把脚号写进消息，别让下一次尝试
看起来像另一个新故障。一个 pad 只能挂一种发生器，切 backend 必须拆干净重建。

另外：rp2 固定频率模式的 PWMOut 写 .frequency 会抛 Invalid variable_frequency，
固件改成频率变化时 deinit 重建。mpy 的 asyncio 端口本身是队列轮转调度器，
create_task 并发没有缺陷（早前"gather 按顺序 await 饿死子任务"的诊断已被真机证伪）。

SPI 这几条同样是 tools/spi_probe.py 实测出来的，别再照数据手册推：
构造函数只收位置参数（`baudrate=` 直接 TypeError，`half_duplex=` NotImplementedError），
只给 SCK 会被拒（Must provide MISO or MOSI pin），所以速率和模式要建好之后在锁内
`configure()`（不锁就报 Function requires lock）；`.frequency` 回的是分频器实际到达的值，
150 MHz 除以偶数、上限 75 MHz，所以 `hbaud` 必须回给主机；
可路由的 (SCK, MOSI, MISO) 组合是静态表 SPI_GROUPS，它是 gpio.h F1 列的完整转录，
GP0..GP28 行另有 tools/spi_probe.py 的上板实测逐行确认过；30..47 是 QFN-80 专属行，
发 caps 前按 gp 投影。开机不扫描（穷举要 1600+ 次构造）。

引脚相关的四条实现约束（每一条都能在上面引的官方源码里核到，动引脚逻辑前先看）：

1. 可寻址集合 = 封装 GPIO ∩ board 里声明过的脚。Pin 对象身上没有号码可读，号码从声明名解析：
   GPn 直接读；只有 ADC 别名的脚（Pico 2 的 A3/VOLTAGE_MONITOR）按 ADC_BASE + 通道号算，
   ADC_BASE 取 A0 背后那个脚的号码，于是 A3 就是 GP29。固件开机扫成 GP_NAMES / GPS，
   NUM_PINS 取最大脚号 + 1。这张表可能有洞（Pico 2 W 不声明 GP23/24/25），
   所以 _pin() 对声明里没有的脚抛 board has no GP%d，而不是让它撞 AttributeError。
2. ADC 窗口来自 platform_defs.h（ADC_BASE_PIN / NUM_ADC_CHANNELS），不是"26..28"这种写死的范围；
   TEMP 走的也不是 AnalogIn，是 microcontroller.cpu.temperature 反推的 16 位码。
3. UART / I2C / PWM / SPI 的合法性一律按脚号算（UART ((n+4)//8)%NUM_UARTS、I2C (n//2)%2 与
   奇偶、PWM (n//2)%8 且 16 脚绕回、SPI 查组），不要把这些规则摊成界面里的 if 特判。
4. 主机侧位掩码到 48 位：JS 的 1<<n 在 n>=32 会绕回， pins.ts 里统一用 2**n 与
   Math.floor(mask/2**n)%2 读写位（48 位仍小于 Number.MAX_SAFE_INTEGER，双精度是精确的）。

界面侧的分层与依赖方向见仓库 README 的"架构"一节，这里不重复。
一条硬约束：层间依赖单向向下，workbench/ 下每个功能是一个 FunctionDef 插件，
新增总线功能 = 写 def(+driver) 并注册进 defs 数组，同时在固件 COMMANDS 表里注册命令。

[提交约定]

git commit 标题一律用 type(scope): subject，例如 feat(uart): ...、fix(fw): ...。
固件版本号写在 code.py 的 VERSION 常量里，随功能变更一起提升。

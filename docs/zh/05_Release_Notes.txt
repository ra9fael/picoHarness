PicoHarness 版本说明

固件版本号写在 code.py 的 VERSION 常量里；上位机版本以仓库提交为准。
界面与固件要配套：旧固件收不到新命令，会回 "unknown cmd"。


[20261014 0.1.19-cfg]

配置有了第三个去处：板子的卷。之前只有两份——浏览器 localStorage 和你手动导出的 JSON 文件，
这一版加上 G:\config.json，命令是 `cfg.get` / `cfg.save` / `cfg.clear`，
`ready.caps` 里对应新增 `cfg`（`path` + `max_bytes`，上限 65536）。

固件是保险箱，不是读者：`cfg.save` 只确认送来的是合法 JSON、顶层带 `pins` 数组，然后原样存，
不解析任何一个字段，**也不在上电时照它给引脚编程**。所以快照格式的主人仍然只有一个
（`src/ui/model/store.ts`），导出的文件、浏览器那份、板子这第三份是同一串字节，
固件升级不会因为读不懂而丢用户的东西。写入是临时文件改名 + 回读核对字节数 + `os.sync()`：
中途掉电或拔线，卷上要么是完整旧配置，要么是完整新配置，不会剩半份。回读核对是按
`os.stat()` 的第 6 个元素取字节数的——CircuitPython 返回的是裸元组，没有 `.st_size` 这个属性。

板子上写得进，靠的是 boot.py 新增的一行
`storage.remount("/", readonly=False, disable_concurrent_write_protection=True)`。没有它，
CircuitPython 眼里的卷是只读的，`cfg.save` 回 `OSError: [Errno 30] Read-only filesystem`，
而其它一切照常——读命令、引脚、总线都不受影响，只有写会暴露这个问题。这一行是有代价的，
两个版本都在 Pico 2 / 10.3.1 上实测过：只写 `readonly=False` 的话 Windows 侧就再也写不进 G:，
从资源管理器拷固件这条路断掉，只能快速按两下 RESET 进安全模式救回来（安全模式既不做 boot.py
也不做 code.py）；带上后面那个开关则两边都能写，代价是 Windows 显示的是卷的缓存，板子写了什么
要等卷重新读一次才看得见。所以核对板子上那份配置请用界面的**从板子载入**，别在资源管理器里找
`config.json`；要往 G: 拖文件之前先按一次 RESET，让两个视图对同一片空闲簇达成一致。
boot.py 只在硬复位时执行，Ctrl-D 软复位不跑它。

新增命令 `reset`，COMMANDS 表从 27 条变 28 条：先把 `{"reset":"pending"}` 答出去，等 0.25 秒
让字节走完 CDC 缓冲，再 `microcontroller.reset()`，效果与按 RESET 键相同——boot.py 会重跑。
部署动过 boot.py 之后不用再走到板子前面。界面这一版还没有触发它的按钮；mock 里同样备了这条
命令，离线夹具不会回 "unknown cmd"。

界面顶部**配置 ▾**菜单多一条分隔线和三行（保存到板子 / 从板子载入 / 删除板子配置），
点"连接设备"时按这份优先级走：板子上有文件而工作台是空的 → 直接载入并只打一行日志；
两份内容相同、或板子上没有文件 → 什么都不说；都有内容且不同 → 弹确认框，
取消就留下浏览器这份并写明"板子上那份未改动"。确认框只在点连接时出现，
链路已建立时按 RESET 或保存 code.py 不会把你刚答过的问题再问一遍。
板子那一份**只在手动保存时改写**：载入不回写，清空配置也不碰它。
旧固件没有 `caps.cfg` 时这三行压根不出现，界面也就发不出它答不上来的命令——
与 `caps.pwm_pio` 缺席时收起 HW/PIO 选择是同一条规则。

协议之外的一致性修复：mock 的 `gpio.state` 之前把所有 GPIO 掩码报成 0，于是任何已绑定的脚
每秒都被判成漂移、重发一条 mock 不认的 `gpio.cfg`，冒烟测试里刷一屏
`unknown cmd: gpio.cfg`。现在 mock 也按 owner[] 记账，GPIO 泳道能离线测了。

存 / 载 / 重启后仍在 / 三种拒收（非 JSON、不是快照、超过上限）/ `reset` 之后主机重新拿到
`ready`，这一整套由 `tools/vault_probe.py` 在 Pico 2 上实跑过，插板即测。

已知限制：Web Serial 没有删除卷上文件的接口，"删除板子配置"只能删掉 code.py 认的那个路径，
真要把 G:\config.json 从卷上抹掉还是得在资源管理器里删；重刷 UF2 或格式化整卷也会带走它。


[20261013 0.1.18-pio]

PWM 多了一台发生器：状态机自己数的 PIO。硬件 slice 的实测下限一直是 9 Hz
（填 1..8 Hz 板子都跑 9），低于 1 Hz 更是直接拒；这一版把下限推到 0.0174553 Hz，
用的是一段 8 指令的 PIO 程序——SM 每个 tick 走一格，高/低两段各一个 16 位计数器，
一个周期固定再花 8 格，于是 SM 时钟窗口（实测 2288 Hz–150 MHz）换算成
0.0174553–15,000,000 Hz 的输出频率。上板实测：0.1 Hz 一路稳跑（回报 0.099986 Hz，
偏差 0.014 %），GP0..GP11 十二路 0.1 Hz 同时开全部正常，第 13 路被拒并回
`RuntimeError: no free PIO state machine (12/12 in use)`；硬件那路做交叉核对，
GP14 请求 5 Hz 仍回报 hfreq 9。

窗口两端不是写死的数字。ready.caps 新增 `pwm_pio`：`pins`（RP2350 每个 GPIO 都在 PIO
矩阵里，所以就是可寻址集合本身）、`max_sm`，加上 `tick_cycles`、`fixed_cycles`、
`counters`、`clk_min`、`clk_max` 五个窗口参数，主机按 `clk_min/(2*counters+fixed)` 和
`clk_max/(fixed+2)` 现算上下限。换芯片或改指令段，上位机不用跟着改。
`lib/adafruit_pioasm.mpy` 不在时 `pwm_pio` 整个是 `null`——rp2pio 是内置的，外挂的只有
这个板内拼 asm 的库——缺件不致命：code.py 照跑，界面收起 HW/PIO 选择，硬件 slice 不受影响。

协议变化：`pwm.cfg` 新增 `backend`（`"hw"` 默认 / `"pio"`），`hw` 的 `freq` 仍只吃整数、
`pio` 的可以是小数，越界分别报 `below PIO floor` / `above PIO ceiling`；state 新增
`cfg_pio_pwm`（这些 PWM 脚里哪几路在跑 PIO）和 `pio_sm_free`（剩余状态机数，预算是整块芯片的），
`pwm.<脚>` 新增 `be`。`pwm.stop` 两种发生器一起拆，PIO 那路把状态机还回预算。

改频率和改 backend 都走 deinit + 重建，这不是风格问题：正在跑的状态机仍照它那条 4 深的
TX FIFO 出货，实测新计数要五个周期后才见效（重启后仍要四个），所以重建并在跑之前 arm，
第一个周期就是新参数。构造函数抛异常的那台 SM 会把引脚占到复位为止、又不退还预算，
于是错误消息写明脚号（`GP%d PIO start refused`），免得下一次在同脚上的尝试看起来是
另一桩新故障。

上位机：频率框左边新增 HW | PIO 分段按钮，逐通道独立、默认硬件；被拒的错误只写在那一颗
芯片下方（红字 + 日志一行），界面不会替你改回硬件——选择是用户的，`cfg_pio_pwm` 如实回报。
频率夹取方向改为朝里：窗口端点是精确除法（PIO 下限 0.01745533…），按四舍五入落到 0.017455
就会向固件要到低于下限的时钟，这一版实测修掉。持久化快照给 PWM 通道加了 `b` 字段
（缺省/0 是硬件，1 是 PIO），旧快照不带 `b` 读作硬件，配置里没有 `caps.pwm_pio` 时存的 PIO
通道会被降级回硬件并夹进硬件窗口。

文档同步：01 §2.2 补 `adafruit_pioasm` 缺件行为、§4.4 新增 4.4.1（HW/PIO 对照表、两端点算式、
12 路实测、第 13 路拒绝原文）；02 的 caps/state/`pwm.cfg` 三处补齐新字段并说明窗口来源；
03 的常见错误加了预算耗尽、窗口越界、缺 pioasm 三条；04 记下 PIO 的实测约束。
验证：`tools/pio_fw_check.py` 上板跑通（12 路共存 + 拒绝 + 掩码 + 预算归还），
`tools/pio_pwm_probe.py`、`tools/pio_bg_probe.py`、`tools/pio_stage0a.py`、`tools/pio_pwm_read.py`
是这一路的探针，`tools/make_mock.mjs` 把 mock 注入 dist/index.html 变成可离线点的 mock.html。

[20261013 ui-bus-badges]

固件版本不变（0.1.17-gp29），这一版只动上位机。

点总线卡片里的空槽，引脚池会反过来告诉你谁能进：能进的脚发光、其余变暗，
点亮用的判定和拖放用的是同一张 caps 表，所以亮起来的一定进得去。
I2C 按序对算（SCL 落在 GP29 时，只亮同一路外设那侧的偶数脚）；UART 按实例算
（TX=GP28 之后 RX 只剩 1/3/13/15/17/19/29，GP27 属于另一路 UART，界面把它按暗，
这正是真机 `UART(TX=28, RX=27)` 报 Invalid pins 的那条规则）；SPI 按引脚组算
（SCK=GP2 之后 MISO 只剩 0/4/16/20，跨组的 8/12/28 全暗）。第二下点亮的芯片即完成
绑定，点空白处取消聚焦，点已经有脚的槽是解绑而不是聚焦。

芯片角标补上 SPI 的三个数据角色：CK / DO / DI，分别来自 caps.spi.groups 的
sck / mosi / miso 行；每个字母都带 tooltip，写明它是哪张表给的。角标只在设备真的
上报了那张表时才出现，所以旧固件下这三类字母整批不见——那不代表脚不能用，
01 手册 §4.1 把"没角标"和"不能用"区分开了。CS 没有角标：固件把片选当普通输出脚做，
任何空闲的 GP 都能当。

01 手册新增 §4.1"角标怎么看"（角标→caps 字段对照表 + 四条最容易误读的地方），
§4 原有各小节顺延为 4.2..4.9，02 手册里指向 PWM 的锚点跟着改成 #44-pwm。


[20261013 0.1.17-gp29]

Pico 2 上的 GP29 进池子了。它从不以 "GP29" 出现——板级表只把它声明成 A3 /
VOLTAGE_MONITOR，而 CircuitPython 的 Pin 对象身上读不到号码，所以原来那条
"名字里必须有 GPn" 的过滤器把它当成不存在。现在固件扫 board 上所有 Pin 对象、
按身份去重：号码优先从声明名里的 GPn 读；只有 ADC 别名的脚按 ADC_BASE + 通道号补，
ADC_BASE 就是 A0 背后那个脚的号码（这块板上 A0 声明成 board.GP26_A0，于是 A3 = 29）。
整条规则是从设备上算出来的，没有按板子写死任何表。

上板实测 GP29 全能，能力表因此变宽：caps.adc 多了 29，读上来是 VSYS/3
（raw 31815 → 1.600 V → VSYS ≈ 4.80 V）；caps.pwm 到 30 个脚；caps.uart.rx 多了 29；
caps.i2c_pairs 多出 SCL=29 的 8 对，实测 29/28 报的是"没有上拉"，说明序对本身合法。
协议侧逐条走通：adc.cfg、pwm.cfg（回报 hfreq 990）、gpio.cfg 把它当输出、
uart.cfg tx=28 rx=29 全部接受。

顺带钉住两条 UART 实测：UART(TX=GP28, RX=GP27) 报 Invalid pins，不是奇偶规则错，
而是 28 在 UART0、27 在 UART1，跨实例配不成对；单看 28 能当 TX、27 能当 RX，
各自都建得起总线。tools/caps_audit.py 的真机半程现在把这张表与文档逐条对账，全绿；
碰到没有 gp 字段的旧固件，它直接说"先部署新固件"，不再拿假的连续范围去比。

界面与文档同步：引脚池按 caps.gp 自动多出 GP29；01/02/04 里"可寻址集合"的口径
从"板级命名为 GPn 的脚"改成"板级声明的脚，号码读自声明名，只有 ADC 别名的按
ADC_BASE+通道补号"，并写入上面的实测数据。


[20261012 0.1.16-spi]

加 SPI 总线。固件新增 spi.cfg / spi.release / spi.xfer 三条命令，read_state 新增
cfg_spi 与 spi 列表，ready.caps 新增 spi 对象（groups / max_buses / max_cs / baud_ceiling）。

引脚合法性先由 tools/spi_probe.py 上板实测，再与 pico-sdk hardware/gpio.h 的 F1 列逐行对账，
两者一致。穷举每个有序 (SCK, partner) 组合，53 个被接受，正好落在两组里；
1571 组配对报 Invalid pins，100 个三元组是这两组的笛卡尔积。结论写进静态表 SPI_GROUPS，
开机不扫描（扫描要 1600+ 次构造调用，而答案是芯片属性，不会因接线而变）。

端口行为决定了 API 形状：构造函数只收位置参数（baudrate= 直接 TypeError，
half_duplex= NotImplementedError），只给 SCK 会被拒（Must provide MISO or MOSI pin），
因此速率与模式在建好之后于锁内 configure()。半总线（缺 MOSI 或缺 MISO）合法，
和 UART 一个口径。片选不属于 busio.SPI：固件把每路 CS 当普通输出脚，空闲为高、
事务期间拉低，于是一条总线最多带 SPI_MAX_CS=4 路器件；CS 同样登记 owner="spi"，
在界面上算占用，防止主机用 gpio.set 在事务中间改动选中状态。

时钟沿用 PWM 的 hfreq 诚实口径，字段名 hbaud：rp2 只能把 150 MHz 除以偶数整数，
上限 75 MHz，所以请求 2 MHz 实跑 1973684 Hz、10 MHz 实跑 9375000 Hz，卡片把这行打在结果里。
这个口的全双工只有 write_readinto() 一个调用且要求等长缓冲区，
固件把短的写用 0xFF 补到 max(len(w), r)，读回截前 r 字节。

界面新增 SPI 泳道（总线卡片：SCK/MOSI/MISO 三个数据槽 + CS0..CS3）与事务台，
一次一笔原始字节事务，支持"保持片选"做分两段的事务、片选下拉选"—"表示全程不动片选。
跨组的脚拖不进去，第三路总线在界面就被挡下。配置随其它总线一起进 localStorage，
漂移对账把 cs 顺序、baud、mode 都算进签名。

同一版里把"这块板有哪些脚"彻底按官方文档重做了一遍（不提升版本号）：
可寻址集合 = 封装 GPIO 数 ∩ CircuitPython 板级命名，固件开机扫 board 得出并作为 ready 的新字段
gp 上报（Pico 2 W 就有洞：没有 GP23/24/25，GP29 只以 A3/VOLTAGE_MONITOR 存在）；
caps.pins 的含义随之改成"最大可命名脚号 + 1"，不再是引脚个数。SPI_GROUPS 是 gpio.h F1 的完整
48 脚转录，发送前按 gp 投影，界面 / mock / 固件读到的都是同一份集合，任何写死的脚数都被拿掉。
主机侧位掩码改成 2**n 读写（1<<n 在 n>=32 绕回），48 位仍在安全整数范围内。
新增 tools/caps_audit.py：--static 用文档规则跑满 48 个脚号自校并解析固件里的 SPI_GROUPS 与
UART 实例式，接上板子时再与真机 caps 对账。双语手册里 PWM slice、ADC 窗口、I2C/UART/SPI
的合法性全部改成引 gpio.h / platform_defs.h / CP common-hal 源码的确切条件——
I2C 走硬件 DW_apb_i2c 而非 PIO（早前版本说明里写成 PIO，那句是错的）且配对不要求相邻，
UART 偶 TX 奇 RX、实例 ((n+4)//8)%NUM_UARTS，
PWM 到 GP16 会绕回 slice 0（"不相邻"不等于"不同 slice"）。


[20261012 0.1.15-pwmhz]

固件把 PWM 的真实频率说出来。rp2 的分频器只能生成 125 MHz/(div×(top+1))，实测下限 9 Hz：
请求 1..8 Hz 全部跑 9，高频也量化（1000→990、2000→2035）。read_state 的 pwm 条目新增
hfreq（slice 实际频率），freq 仍是你请求的值。界面上频率框随之描成琥珀色并给出 tooltip，
偏差超过 5% 时再往日志写一条。低于 1 Hz 照旧由固件拒绝（PWMOut 只吃整数）。

顺带修掉一个会致盲的坑：pwm.cfg 建对象失败时（同 slice 要第二个频率会回
RuntimeError: Conflicting settings for shared resource）引脚已 claim 成 pwm 却没有对象，
read_state 因此抛 TypeError，之后整个 gpio.state 都不可用。现在失败路径退还所有权。

界面修复：点芯片再点泳道从前只对 I2C/UART 的卡槽有效，四条 per-pin 泳道只挂了
dragover/drop，点亮着的泳道毫无反应——而选中提示的文案正是"点击高亮泳道绑定"。
现在 click 与 drop 走同一个 assign 路径，点引脚池也能解绑选中脚。附带修掉提示里
"GPGP4" 这种重复前缀（pinLabel 已含 GP，文案又写死了一个）。

code.py 的 JSON 行协议与二进制帧走 data 口，console 口还给 CircuitPython 自己

没挂上时按钮还能手点。状态灯把端口角色摆在明面上：
"已连接 · 双口 · 日志口 ✓"，单口板显示"已连接 · 单口·旧模式"并在页面顶部常驻一条警告。
进入 REPL 只动 console 口，数据口的连接不会断，所以退出 REPL 无需重新选口；
但要说清楚：REPL 靠 Ctrl+C 停掉 code.py，这段时间协议**没人应答**，双口只是免掉了重选端口。

控制台新增"协议流"开关：默认关闭，打开后把协议端口的原始 JSON/二进制字节也写进终端，
用于对着线上格式查协议。

顶部新增"配置 ▾"菜单：导出配置为 picoharness-config-<时间戳>.json、导入并立刻下发、
清空前先确认。连接状态下的握手会用设备能力表核对绑定，把这块固件带不动的脚解除并在控制台点名，
所以从别的板子拷来的配置不会再"看着在跑其实一直失败"。

失败提示改成"现象 → 原因 → 下一步"三段式，例如"未找到协议端口"直接给出缺 code.py、
boot.py 没硬复位两种原因和对应的动作。

兼容回落保留一个版本：G: 上没有 boot.py 时 usb_cdc.data 为 None，固件回单口；
上位机 hello 失败即走"重启设备等 ready 广播"的老路径。下一版不再支持单口模式。

两条真机约束：boot.py 只有硬复位才生效（Ctrl-D 软重启不会重跑它）；
CircuitPython REPL 收 \r\n，只给 \n 的行会被回显但永不执行。

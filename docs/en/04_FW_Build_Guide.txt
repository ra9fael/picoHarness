PicoHarness Build Guide

This document covers how to produce the deliverables from source, how to deploy to the board,
and how to verify after a change. For usage see "01_GUIApp_FW_Manual", for the interface
definition see "02_Library_User_Guide".


[Prerequisites]

The following versions are verified to work:

Node.js: 24.18.0
npm: bundled with Node
Browser: desktop Chrome or Edge (needs the Web Serial API)
Board: Raspberry Pi Pico 2 (rp2350a)
Device firmware: CircuitPython 10.3.1 (board_id: raspberry_pi_pico2)

The repository depends only on esbuild, typescript and two frontend runtimes (xterm.js).
Install with:

    npm install

The device side needs an asyncio implementation (CircuitPython does not ship one). Install it
into the board's lib directory with circup:

    circup install asyncio

Afterwards lib/asyncio/ and lib/adafruit_ticks.mpy should exist under the CIRCUITPY volume.
The PIO PWM generator additionally needs lib/adafruit_pioasm.mpy (circup install adafruit_pioasm).
The repo keeps a copy of the same file at src/fw/lib/adafruit_pioasm.mpy (the circup-installed original,
sha256 27e3d1fd56ec66c63119acae6b3ef9da5fbe25ed8308647bd549206aa9bf4687) for hosts where circup is not an option.
rp2pio itself is already compiled into the CircuitPython 10.3.1 RP2 build, so there is nothing to install for
it; without adafruit_pioasm, code.py still runs, caps simply reports no pwm_pio and the UI hides the HW/PIO
choice.
From now on, touch device libraries only through circup; never copy them by hand.


[Build steps]

    npm run build

The artifact is the single file dist/index.html (all JS/CSS inlined, about 400 KB). Double-click
it and it works straight from file://; no server needed. dist/ is git-ignored, do not commit it.


[Firmware deployment]

The firmware is two files: src/fw/boot.py (enables the second CDC port) and src/fw/code.py (the
protocol itself). Both are copied to the root of the CIRCUITPY volume (written as G: below):

    cp src/fw/boot.py /g/boot.py
    cp src/fw/code.py /g/code.py

Note:

Writing the file triggers an immediate soft reset; the live Web Serial connection drops, so
click Connect again in the UI.
boot.py only takes effect on a hard reset (press RESET or unplug/replug — a Ctrl-D soft reboot does
not re-run it). After copying boot.py, hard-reset once, otherwise the board still exposes a single
CDC port and caps.usb.data stays false.
If a main.py exists in the G: root, CircuitPython never runs code.py (main.py takes priority).
boot.py should contain nothing but usb_cdc.enable(...): do not claim GP0/GP1 or build bus objects
there, because the pin arbiter lives in code.py and boot.py would grab the serial console.
If G: has no lib/, circup did not install successfully and code.py will fail to start with an
ImportError.

With dual CDC the board shows up as two COM ports: the console port belongs to CircuitPython
(banner, print, tracebacks, REPL) and the data port runs this project's JSON-lines protocol and
binary frames. Both share one VID/PID (0x2E8A:0x000B), so neither Device Manager nor
navigator.serial.getInfo() can tell them apart — only a nonce ping can. The UI does that
identification automatically; when debugging by hand, never guess from the COM number.


[Type check]

The repository has no tsconfig.json. Running npx tsc directly reports TS5058, so the parameters
must be given explicitly:

    npx -p typescript tsc --noEmit --strict \
        --module esnext --target es2020 --moduleResolution bundler \
        --lib es2020,dom --skipLibCheck src/ui/main.ts

npm run build goes through esbuild, which only bundles and does no type checking. After any
change to a .ts file, run the command above separately.


[Verification chain]

After changing the firmware (code.py), do these in order:

1. Syntax check
       .venv/Scripts/python.exe -m py_compile src/fw/boot.py src/fw/code.py
2. Deploy to the board (see above)
3. Query the device directly with pyserial to confirm the new commands and fields really exist.
   With dual CDC there are two ways to do this, and one is much simpler:
   - The easy way: run tools/serial_probe.py with no arguments. It discovers both ports by VID/PID,
     tells them apart with a nonce ping, restarts code.py on the console port, reads the ready
     broadcast from the data port, then exercises hello / ping / echo.
   - Hand-written scripts: the port that answers {"cmd":"ping"} with your nonce is the data port
     (protocol); the other is the console port, which only takes control bytes and REPL statements.
     Open the data port and keep a reader attached *before* you restart anything — CircuitPython
     throws CDC output away while no host holds the port, so the boot-time ready broadcast reaches
     only a reader that is already there. To restart code.py: send \x03 to the console port to stop
     the running program → wait 0.5 s → send \x04 → the second \x04 covers the case where the first
     only woke the REPL.
     REPL statements must end with \r\n; a line ending in \n alone is echoed but never executed.
   Use the python from the venv for the script (pyserial is installed only in .venv; the system
   pip has no network access). Write output via sys.stdout.buffer.write, because a GBK console
   blows up on UTF-8. On startup the device first sends an ANSI/OSC escape that sets the
   terminal title; it is glued to the front of the ready JSON with no newline, so the script
   must strip it with a regex or locate the braces to extract the JSON.

After changing the UI, do these in order:

1. Type check (see above)
2. npm run build
3. Open dist/index.html in a browser for a DOM smoke test: assert that elements exist, that
   interactions work, and that the console is clean. Most logic can be tested without a board —
   lane binding, drag highlighting and persistence do not depend on the device.
   Port logic (protocol-port discovery, log port, REPL) can be exercised with a fake
   navigator.serial: two in-memory FakePorts, one answering pings and one answering only the
   REPL, covers the whole chain without hardware.
   Clear localStorage when the test ends (keys: picoharness-config-v1, picoharness-scope-v1).
4. If any .md in README or docs/ changed: npm run docs:check. It resolves every relative link
   and #anchor against GitHub's heading-slug rule and exits non-zero on a dead target — this one
   has to pass before a release.

[Troubleshooting criteria]

The UI sends a new command and the device answers "unknown cmd", or the gpio.state reply is
missing a new field, or ready.caps has no uart/i2c_pairs/spi — that is not a frontend bug, it means
G:\code.py is still the old version. Compare the VERSION string in the device-side code.py with
the source and copy the file once more.
Only one COM port appears, or ready.caps.usb.data is false — G:\boot.py was not copied, or the
board was not hard-reset afterwards (Ctrl-D does not count).
ready.caps.spi disagreeing with what a sweep would find — that is the static SPI_GROUPS table, a full
transcription of the F1 column of pico-sdk hardware/gpio.h (whose GP0..GP28 rows were additionally
confirmed on the board by tools/spi_probe.py, row for row). There is deliberately no SPI sweep at boot.
Note that the table is projected onto caps.gp before it is sent: a pin vanishing from a group usually
means the board definition does not declare it, not that the table is wrong.
A pin missing from the UI pool, or a pin present in a caps array but not clickable — check whether
ready.gp exists and contains it. gp is the set of pins this board can reach, computed from the Pin
objects board exposes; if it is absent, G:\code.py is still the old version.
The offline cross-check is tools/caps_audit.py: --static lays the rules read from gpio.h,
platform_defs.h and the CircuitPython sources over all 48 pin numbers and parses SPI_GROUPS and the
UART instance formula straight out of code.py; with a board attached it also compares the live caps.

[Firmware implementation notes]

The main loop is an asyncio task group: command_reader on stdin, gpio_monitor for edge pushes,
adc_monitor for deadband pushes, adc_streamer for the batched waveform feed. Each coroutine is
wrapped with create_task first and the handles are then awaited via gather(t1, t2, ...). The gather
in this mpy port accepts Task objects only; passing bare coroutines trips a "missing await"
assertion inside sleep_ms.

Four constraints established on real hardware, known before touching the scheduler:

1. sys.stdin.read(1) blocks until at least one byte arrives. It is not the non-blocking
   "returns None when empty" idiom. Ungated, command_reader freezes the whole event loop on its
   very first step and every sibling task starves (that was the real cause of the ADC showing no
   readings). The data port behaves the same way: gate on in_waiting before read() and set
   DATA.timeout = 0. The single-port fallback still registers stdin with select.poll() and gates
   each read with while poll(0):.
2. busio.UART defaults to timeout=1000 ms, so a single empty read stalls the cooperative loop.
   Buses are created with timeout=0.
3. On USB CDC, print(..., flush=True) raises OSError [Errno 22] after every write (the text still
   goes out). Do not flush explicitly.
4. usb_cdc.Serial is a binary stream: read() returns bytes and write() takes a bytes-like, while
   sys.stdin is a text object. Whenever one code path feeds both, decode with
   decode("utf-8", "replace") first — otherwise the same buffer raises TypeError and, on the
   fallback path, splits multi-byte characters.

The PIO PWM path has its own set of measured findings (tools/pio_pwm_probe.py, tools/pio_bg_probe.py,
tools/pio_fw_check.py): rp2pio is built in, and assembling asm on the board is lib/adafruit_pioasm.mpy's job,
so the firmware has no host-side build step at all; one 8-instruction program spends a fixed 8 ticks per
period, the two count registers are 16 bits each, and the measured SM clock window of 2288 Hz – 150 MHz
therefore becomes 0.0174553 – 15,000,000 Hz of output frequency. All 12 SMs on the chip can coexist (Stage 5
ran 12 channels at 0.1 Hz at once). A running SM keeps honouring its 4-deep TX FIFO, so a count written
straight in only lands five periods later; pwm.cfg consequently deinits and re-arms every PIO channel and then
uses background_write(loop=...). An SM whose constructor raises still claims its pin until reset but does not
give the budget back, so the error names the pin — otherwise the next attempt on that pin looks like a new,
unrelated failure. A pad hosts one generator at a time, so switching backend must tear the old one down first.

Also: writing .frequency on an rp2 fixed-frequency PWMOut raises Invalid variable_frequency, so the
firmware deinits and rebuilds the object when the frequency changes. The mpy asyncio port is a
queue-rotating scheduler and create_task concurrency on it is sound (the earlier diagnosis that
"gather awaits children in order and starves them" was disproved on hardware).

The SPI constraints below came out of tools/spi_probe.py on the board as well, so do not re-derive
them from the datasheet: the constructor takes the pins positionally (baudrate= raises TypeError,
half_duplex= raises NotImplementedError), a bare SCK is refused with "Must provide MISO or MOSI pin",
so speed and mode are applied afterwards with configure() while the bus is locked (without the lock
it answers "Function requires lock"). .frequency reports the clock the divider actually reached —
150 MHz over an even integer, 75 MHz ceiling — which is why hbaud has to travel back to the host.
The routable (SCK, MOSI, MISO) sets live in the static SPI_GROUPS table — the complete F1 column of
gpio.h, with its GP0..GP28 rows confirmed on hardware by tools/spi_probe.py, while 30..47 are QFN-80
only and are projected away through gp. They are not swept at boot: the exhaustive version is 1600+
constructor calls.

Four pin-related implementation constraints, each traceable to the official sources quoted above:

1. The addressable set is package GPIOs ∩ the pins the board declares; the firmware reads it off
   board at boot into GP_NAMES / GPS, with NUM_PINS = highest reachable number + 1. A Pin object
   carries no readable number, so the number is parsed out of the declared name: "GPn" reads
   directly, and a pin that only has ADC aliases (A3 / VOLTAGE_MONITOR on the Pico 2) is numbered
   ADC_BASE + channel, ADC_BASE being the pin behind A0 — which is how A3 becomes GP29. That table
   can have holes (a Pico 2 W declares no GP23/24/25), which is why _pin() raises
   "board has no GP%d" instead of letting the code trip over an AttributeError.
2. The ADC window comes from platform_defs.h (ADC_BASE_PIN / NUM_ADC_CHANNELS), not from a hardcoded
   "26..28"; and TEMP is not an AnalogIn either — it is microcontroller.cpu.temperature inverted into
   a 16-bit code.
3. UART / I2C / PWM / SPI legality is computed from the pin number (UART ((n+4)//8)%NUM_UARTS, I2C
   parity plus (n//2)%2, PWM (n//2)%8 with the wrap at GP16, SPI by group lookup). Do not spread those
   rules into scattered if-special-cases in the UI.
4. The host-side bitmasks go up to 48 bits: JS 1<<n wraps for n>=32, so pins.ts reads and writes bits
   with 2**n and Math.floor(mask/2**n)%2 (a 48-bit mask stays under Number.MAX_SAFE_INTEGER, so the
   double arithmetic is exact).

The UI layering and its dependency direction are in the "Architecture" section of the repository
README; not repeated here. One hard rule: dependencies point one way, downward. Each function under
workbench/ is a FunctionDef plugin, so adding a bus function means writing a def (+ driver) module and
registering it in the defs array, plus registering its commands in the firmware COMMANDS table.

[Commit convention]

git commit titles always use type(scope): subject, for example feat(uart): ..., fix(fw): ....
The firmware version lives in the VERSION constant in code.py and is bumped together with the
feature changes.
